## 0. How to use this document

This document defines the implementation direction for the new clean TGVF project. It is not the final paper and it does not freeze every research hyperparameter or RL/replay contract. Its purpose is to define the technical skeleton while keeping unresolved research choices explicit and configurable.

Authority order for implementation is:

```text
AGENTS.md
→ docs/PROJECT_TASK.md
→ docs/OPEN_IMPLEMENTATION_CONTRACTS.md
→ this framework-skeleton specification
```

The following decisions were confirmed on 2026-07-19:

- upstream veRL is the base RL framework; the exact commit and rollout backend
  remain subject to a bounded compatibility spike;
- FSDP2 support is required, while the concrete parallel topology remains
  evidence-based;
- the legacy representation dataset and selected code may be reused under
  controlled provenance, but the native-format training pipeline is new;
- the historical TGVF Adapter checkpoint is not a direct initialization for
  the new representation phase;
- the canonical tool name is `tgvf_focus_tool`, and repeated calls are a
  first-class requirement;
- missing rollout, replay, objective, data, reward, and prompt contracts are
  tracked as explicit `[TBD]` items rather than silently inherited from veRL.
- Qwen3-VL-8B-Thinking at the stable local path is the primary policy target;

Before changing code, Codex must:

# 1. Project objective

Build a clean, reproducible end-to-end reinforcement-learning pipeline in which
a Qwen reasoning VLM can:

1. reason from the original image and question;
2. decide when additional target-conditioned visual evidence is needed;
3. call a native-format TGVF tool with a natural-language `target` argument;
4. receive a new visual observation `D` generated by the newly trained
   native-format TGVF Adapter;
5. continue the original reasoning process after the image observation;
6. call the tool again when useful;
7. produce the final answer;
8. learn this policy with separately identified GRPO and reference-style SDPO
   objectives; any later hybrid requires a new accepted equation.

The primary research goal is not merely valid tool-call syntax. The goal is to
learn useful visual-tool behavior while preserving the base policy's reasoning
capability. The first executable target is Qwen3-VL-8B-Thinking; the model
boundary must also support `Qwen/Qwen2.5-VL-7B-Instruct`.

Conceptual trajectory:

```text
original image + question
        ↓
selected Qwen-VL policy reasoning
        ↓
optional native tool call with target
        ↓
TGVF produces target-conditioned observation D
        ↓
D is returned as a multimodal tool response
        ↓
the same selected Qwen-VL policy continues reasoning
        ↓
zero or more additional tool calls
        ↓
final answer
```

# 2. Decisions that are already fixed

These items are settled and must not be reopened during initial implementation.

## 2.1 Base model families

Use **Qwen3-VL-8B-Thinking** as the primary policy/reference target. The old
project records the current local candidate at:

```text
/nvmesv/dredvpn009/models/hf/Qwen3-VL-8B-Thinking
```

The user confirmed this path is stable. Record the model name and absolute path;
do not scan or hash every weight shard. Processor, tokenizer, chat template,
and native token serialization still require exact golden fixtures and fixture
hashes.

Also support **`Qwen/Qwen2.5-VL-7B-Instruct`** as the required secondary model.
Its local/runtime path is `[TBD]`. Qwen3 and Qwen2.5 may differ in model classes,
processor behavior, vision taps, DeepStack availability/layout, M-RoPE state,
native chat template, cache state, and forward arguments. Put those differences
behind a versioned Qwen VLM family adapter rather than scattering family checks
through the AgentLoop or RL objective.

The implementation is Qwen3-first in execution order, not Qwen3-only in
architecture. Representation artifacts are bound to their base-model family
and model identity; cross-family checkpoint portability is never assumed.

## 2.2 DeepStack

DeepStack is **enabled by default** and treated as part of the main system.

Do not spend early implementation time on a DeepStack-off branch. A DeepStack-off comparison may be added near final paper evaluation, but it is not an early decision gate.

## 2.3 Representation assets are reusable; the native pipeline is new

The legacy representation dataset (approximately 50K samples), selected
representation model/training logic, TGVF Adapter design, and validated
DeepStack integration are eligible for controlled reuse after provenance and
interface review.

Terminology: the representation phase trains the **TGVF Adapter**; a TGVF
Adapter checkpoint stores its weights; the TGVF tool runtime invokes it and
constructs the full native observation state. Do not rename the module to a
“representation producer.”

The representation phase has two responsibilities:

1. `D` should contain visual information relevant to the target.
2. `D` should be readable and useful to the selected frozen/base Qwen model.

The representation dataset does **not** need to satisfy RL-specific requirements
such as medium difficulty, reward variance, or reasoning complexity. Do not add
easy/hard filtering to it merely for policy RL.

The legacy pipeline format, serialization, launcher, and resume state are not
the new representation pipeline. Build a native-format representation pipeline
in this repository and train a new checkpoint. The historical representation
checkpoint is retained only for provenance, Adapter parity, and diagnostic
comparison; it is not a direct initialization for the new pipeline.

## 2.4 No old Stage2 SFT

Do not recreate the old Stage2 trajectory SFT.

The new pipeline is:

```text
representation phase
        ↓
policy RL phase
```

Do not train a fixed intermediate reasoning template before RL.

## 2.5 Native tool format only

Use Qwen’s native tool-calling protocol and chat template behavior.

Do not add new tokenizer tokens.
Do not reintroduce legacy control tokens such as:

```text
<|foveate|>
<|/foveate|>
<answer>
</answer>
```

The main TGVF tool schema is conceptually:

```json
{
  "name": "tgvf_focus_tool",
  "arguments": {
    "target": "a concise natural-language description of the visual evidence to inspect"
  }
}
```

The model should answer normally using the selected family's pinned native Qwen
output pattern after it has enough evidence.

## 2.6 Multiple tool calls are a first-class requirement

The initial AgentLoop must support repeated calls:

```text
reasoning → tool call → D1 → reasoning → tool call → D2 → reasoning → answer
```

Do not hardcode one tool call per sample.

A configurable safety cap is required only to prevent runaway loops during early RL. The cap must be greater than one, must not be presented as a method limitation, and must not become an early ablation axis.

## 2.7 Prompt philosophy

The tool prompt must be short, stable, and native-format.

It should explain only:

- what the TGVF tool does;
- the `target` argument;
- that the tool may be used multiple times;
- that reasoning should continue after each returned observation.

Do not run a broad prompt-ablation program. Do not add many demonstrations by default. The legacy project already showed that example-heavy prompting can cause example copying and target contamination.

Prompt work is an acceptance test, not a main research axis.

## 2.8 Clean project, selective reuse

Eligible for controlled reuse after pinned provenance and parity review:

- Qwen3-VL model modifications that are still required;
- Qwen2.5-VL behavior only through separately pinned sources/fixtures, not by
  guessing compatibility from Qwen3 code;
- DeepStack integration;
- TGVF Adapter and selected representation model/training logic;
- the representation dataset after provenance and data audit;
- historical checkpoint loading only for parity/reference diagnostics;
- useful evaluation logic after parity verification;
- stable image and benchmark preprocessing.

Do not migrate as mainline components:

- old Stage2 SFT;
- the historical representation pipeline, serialization, launcher, or resume
  state;
- old custom-token format;
- legacy force-mode controllers;
- obsolete target generators;
- prompt experiments;
- temporary scripts with unclear provenance;
- broad experimental branches.

Legacy deterministic target builders may be retained only as diagnostic/oracle utilities, not as the main RL policy.

# 4. External framework strategy

## 4.1 Main RL framework: upstream veRL

Use a pinned commit of upstream `verl-project/verl` as the primary training framework.

Reasons:

- GRPO and other RL objectives;
- FSDP/FSDP2;
- LoRA RL support;
- vLLM and SGLang rollout backends;
- AgentLoop abstraction for multi-turn tool interaction;
- checkpointing, distributed workers, reward routing, and tracing;
- active upstream support for multimodal RL.

Do not build GRPO, FSDP, distributed rollout scheduling, or checkpoint recovery from scratch.

The exact veRL commit may be pinned only after the compatibility-spike task is
approved and completed. Do not depend on an unpinned moving `main` branch in
reproducible experiments.

Here, a compatibility spike is a bounded integration proof, not a framework
selection exercise and not a training run. It must produce evidence for the
selected veRL commit, Qwen3-VL policy/reference forward, multi-turn latent
observations, a `Qwen/Qwen2.5-VL-7B-Instruct` family-adapter fixture, both
target-condition providers, exact rollout/replay log probabilities, the initial
SDPO extension seams, FSDP2, rollout backend, and checkpoint/resume.

## 4.2 SDPO must be included in the architecture from the beginning

The exact reference is fixed:

```text
paper: arXiv 2601.20802v2
repository: https://github.com/lasgroup/SDPO
commit: 7c457fc1b1f636ae794eb0362ba37d4743b06fbc
```

The repository is a modified veRL source tree, not a thin plugin, and does not
identify the corresponding upstream veRL commit. It is therefore the algorithm
and patch-surface reference rather than the production framework pin.

Implementation strategy:

1. keep upstream veRL as the base;
2. map the pinned SDPO commit's patch surface onto the selected upstream veRL
   commit during the compatibility spike;
3. port only the required algorithm components into a small, isolated extension
   layer through maintained/public hooks;
4. establish exact reference text loss/update parity before multimodal use;
5. keep GRPO fully functional when the SDPO execution path is disabled, while
   retaining the SDPO-ready schema and state interfaces from the first skeleton.

Do not replace the project with the SDPO fork. The pinned implementation
explicitly rejects multimodal distillation, simplifies reprompt context to a
text-oriented final-user/response view, depends on veRL's legacy worker path,
and lacks the strict EMA-teacher resume contract required here. These are
compatibility-spike inputs, not defects to hide behind later integration work.

Required SDPO extension points:

```text
teacher-context construction
typed feedback, success, group, and demonstration provenance
per-assistant-turn sampled-token alignment
exact recorded-observation handles for teacher replay
teacher model / EMA / trust-region state and update lifecycle
full-logit or top-k-plus-tail distillation targets
reference-style SDPO loss
explicit pure-GRPO / pure-SDPO / separately-defined-hybrid identity
multi-turn multimodal observation and policy-token masking
checkpoint/resume state for teacher, counters, config, and RNG
```

The pinned implementation's `loss_mode=sdpo` replaces the policy loss. It does
not specify `GRPO + lambda * SDPO`; any hybrid is a new project objective that
requires its own equation, coefficient, normalization, and ablation.

The implementation must keep two concepts separate:

```text
answer judge
→ verifies final-answer correctness

SDPO self-teacher
→ produces token/logit supervision from feedback-conditioned context
```

They are not the same model role.

## 4.3 Rollout engine selection is a technical spike

Do not assume that an older veRL release fully supports:

```text
Qwen3-VL
+ multi-turn tool calls
+ tool responses containing images
+ continued reasoning
```

Implement a short compatibility spike for SGLang and vLLM. Select one primary engine based on actual behavior and throughput; do not fully maintain two production paths before the spike is complete.

Initial preference may be given to the engine with the most reliable multi-turn multimodal support, but the decision must be evidence-based.

## 4.4 FSDP2

FSDP2 support is required. It is a distributed training backend, not an RL
algorithm. The compatibility spike determines the concrete device mesh,
sharding, worker placement, rollout topology, and LoRA/full-policy execution
mode. Failure of a candidate stack to support the required path is a
compatibility blocker, not permission for an undocumented fallback.

The architecture must leave both training scopes possible:

```text
LoRA + FSDP2
full fine-tuning + FSDP2
```

LoRA is the default pilot path; full fine-tuning remains a required later
option. The first proven FSDP2 topology may differ between the two scopes and
must be selected from measured correctness, memory, and throughput.

## 4.5 DeepEyes as a scoped design reference

Use `Visual-Agent/DeepEyes` commit
`11d20c6be32b2cf62c914e0c73a06db2f9a7e3a1` only as a point-in-time design
reference. Relevant patterns include its veRL-based multi-turn tool loop,
dynamic multimodal observations, per-sample tool routing, interleaved Qwen-VL
M-RoPE/masks, data/reward routing, tracing, and independent judge service.

Do not copy its veRL tree or inherit its crop tool, prompt, data assumptions,
reward coefficients, asynchronous-staleness policy, or logprob conventions.
DeepEyes documents Qwen2.5-VL policy models and a
`Qwen/Qwen2.5-72B-Instruct` judge service. This project fixes the secondary
policy model to `Qwen/Qwen2.5-VL-7B-Instruct` and reserves the 72B judge provider
without deploying it in the first pilot. Exact permitted reference topics are
maintained in `docs/EXTERNAL_REFERENCES.md`.

# 5. Required system architecture

A compact suggested source layout is:

```text
project/
├── src/
│   ├── model/       # Qwen family adapters, DeepStack, TGVF, condition providers
│   ├── agent/       # tool schemas, parsers, multi-turn AgentLoop
│   ├── train/       # veRL integration and LoRA/full execution
│   ├── objectives/  # framework-neutral GRPO and SDPO contracts
│   ├── judges/      # optional versioned answer-judge providers
│   ├── data/        # representation loader, RL dataset ingest and audit
│   └── eval/        # task, tool, reasoning, robustness evaluation
├── configs/
├── scripts/
├── tests/
├── docs/
└── AGENTS.md
```

This is a guideline, not a command to create a directory for every tiny abstraction. Prefer a small number of coherent modules over ceremonial fragmentation.

## 5.1 Model layer

The model layer must wrap, not redesign, the validated old-project components.

Required responsibilities:

- expose one versioned family-adapter interface with a Qwen3-VL primary path and
  a `Qwen/Qwen2.5-VL-7B-Instruct` compatibility path;
- load family-specific DeepStack integration when supported and declare its
  exact layout rather than assuming Qwen3 behavior;
- load a newly trained native-format TGVF Adapter checkpoint;
- expose both required target-conditioning providers;
- produce a selected-family-compatible focused observation `D`;
- support LoRA and full training modes;
- reserve a separately gated joint-update extension without changing exact
  rollout-observation replay.

## 5.2 Agent layer

The AgentLoop is the central new component.

It must:

1. receive the original image, question, tool schema, and conversation state;
2. call the rollout model;
3. parse native tool calls;
4. extract the `target` string and exact target token span when needed;
5. invoke TGVF;
6. return `D` as a multimodal tool observation;
7. append the observation without discarding prior reasoning;
8. continue generation;
9. support repeated tool calls;
10. terminate on final answer or safety limits;
11. return complete trajectory metadata for RL and debugging.

## 5.3 Token-history integrity

Preserving the original reasoning history is mandatory.

Avoid this pattern:

```text
decode whole history into messages
→ rerender the chat template
→ retokenize everything
```

when it can change tokenization, remove reasoning content, or alter multimodal positions.

Prefer:

```text
retain generated token IDs and multimodal state
→ append exact tool-response tokens and image inputs
→ continue generation
```

If a backend requires rerendering, it must reproduce the frozen canonical
transcript token IDs, ownership masks, visual layout, positions, and cache
contract exactly. Semantic or visual similarity is not sufficient.

## 5.4 Tool API

Main tool:

```python
TGVFFocusTool(target: str) -> FocusedObservation
```

The AgentLoop should not assume that every visual tool uses the same arguments. Use a small tool registry so that later extensions can add:

```text
image_zoom_in_tool(bbox_2d)
tgvf_focus_tool(target)
tgvf_crop_tool(target, bbox_2d)
```

Only `tgvf_focus_tool` is the current main method.

## 5.5 Focused observation abstraction

Do not assume `D` must be serialized to a conventional image file if the old validated implementation uses features or a custom re-encoding path.

Create one wrapper around the native-format representation output:

```python
@dataclass
class FocusedObservation:
    multimodal_payload: object
    debug_preview: object | None
    metadata: dict
```

The payload must be accepted by the selected family adapter's continuation
path. The debug preview is optional and must not determine training behavior.

# 6. Target conditioning: only two implementations

Do not add a third small text encoder at this stage.

Both implementations below are mandatory capabilities and require fixtures.
The `condition.type` field selects one for a run; it does not remove the other
from the supported architecture.

## 6.1 Contextual hidden-state condition

Use the hidden states corresponding to the generated `target` value inside the full current reasoning context.

Expected benefit:

- includes current question and reasoning context;
- represents the model’s current visual intent rather than an isolated phrase.

Expected cost:

- difficult to retrieve from rollout engines;
- may require an exact actor re-forward;
- slower and more complex;
- may contain irrelevant or incorrect reasoning context.

Correctness-first implementation:

1. retain exact generated token IDs;
2. identify the target token range;
3. re-forward the exact multimodal prefix with the current actor model;
4. retrieve the required hidden states;
5. pass the span to the TGVF Adapter;
6. only optimize this path after correctness is established.

Do not begin by deeply patching vLLM internals unless the simple re-forward path is proven too slow.

## 6.2 Target token-embedding condition

Tokenize `target` alone and obtain the base model input embeddings:

```python
target_ids = tokenizer(target_text, add_special_tokens=False)
target_embeddings = model.get_input_embeddings()(target_ids)
```

Pass these embeddings to the existing TGVF conditioning path.

Do not add a separate text encoder.
Do not add extra learned tokenizer tokens.

## 6.3 Required interface

```python
class TargetConditionProvider(Protocol):
    def build(
        self,
        *,
        target_text: str,
        trajectory_state: object,
        model: object,
        tokenizer: object,
    ) -> object:
        ...
```

Implement exactly:

```text
ContextualHiddenStateConditionProvider
TargetTokenEmbeddingConditionProvider
```

The comparison between these two is a core method experiment.

## 6.4 Target-span correctness

The target span must be identified deterministically.

Required tests include:

- repeated target text elsewhere in the response;
- escaped JSON strings;
- non-ASCII target text;
- multiple tool calls in one trajectory;
- target split across multiple tokenizer tokens;
- empty or malformed arguments.

Do not use a fuzzy string search over a retokenized full conversation as the only implementation.

# 7. Rollout-observation identity and later joint updates

“End-to-end” first refers to the policy learning the complete agent trajectory:
routing, target generation, tool use, post-`D` reasoning, and answering. It does
not imply that the TGVF Adapter must receive gradients in the first
policy RL proof.

For every tool call, rollout materializes main `D`, every D-DeepStack tensor,
layout, positions, multimodal types, masks, and cache state. Policy, old-policy,
and frozen-reference likelihood replay must consume those same recorded
observations. They recompute logits, not the observation. Regenerating `Hq` or
`D` with updated parameters would change the trajectory being compared and is
forbidden.

The accepted initial mode is:

```text
tgvf_update_mode=frozen
→ use the newly trained native-format TGVF Adapter checkpoint as the fixed
  rollout observation generator
→ replay every policy/reference model against the exact recorded per-call D
```

A later joint-update mode remains `[TBD]`. It requires a separately accepted
algorithm specifying parameter versions, stored inputs, gradient flow, update
ordering, and how a gradient-carrying path coexists with immutable rollout
observations. A simple “recompute `D` with the current actor” implementation is
not acceptable.

When that later mode is specified, a gradient-reachability test is mandatory:

- run one tiny training batch;
- report nonzero gradient norms for every intended trainable module;
- verify frozen modules have zero/no gradients;
- fail loudly if the joint-update configuration claims representation gradients
  but they are absent.

Do not silently equate trajectory-level end-to-end policy learning with joint
parameter training of the TGVF Adapter.

# 8. Prompt and native tool protocol

The exact prompt is `[TBD]`. The skeleton must support a versioned prompt
artifact outside canonical dataset records. Once an initial prompt is accepted,
version it, test it, and freeze it unless diagnostics fail.

Suggested semantics, not necessarily exact wording:

```text
You may use tgvf_focus_tool when the current visual evidence is insufficient.
The tool returns a target-conditioned visual observation.
Provide a concise target describing the visual evidence to inspect.
You may call the tool multiple times and should continue reasoning after each result.
Answer normally when ready.
```

Requirements:

- use the selected Qwen family's pinned native tools schema;
- no custom answer tag;
- no custom foveation token;
- no long demonstrations by default;
- no rule-based forced target in normal training;
- support multiple calls;
- keep prompt text outside dataset records when possible and render it by version at runtime.

Prompt acceptance metrics:

- valid tool-call parse rate;
- valid JSON rate;
- nonempty target rate;
- continuation after tool response;
- multi-call capability;
- target/answer-option overlap as a diagnostic;
- no obvious prompt-example copying.

Once these are adequate, stop prompt tuning and move to RL/data work.

# 9. Data plan

## 9.1 Representation data

No RL-difficulty filtering task is required for the retained representation
data.

The approximately 50K legacy representation dataset may be retained after
provenance and data audit, then adapted into the new native-format pipeline.
The old pipeline does not remain unchanged. Do not mix representation-dataset
decisions with policy-RL dataset decisions.

## 9.2 RL data is a separate data line

Do not assume the representation dataset is appropriate for policy RL.

The RL dataset must emphasize:

- verifiable final answers;
- nontrivial reasoning;
- potential utility from additional visual observation;
- a useful mix of success and failure under the base model;
- absence of train/evaluation leakage.

## 9.3 DeepEyes 47K is a candidate source, not a fixed dataset decision

The public `ChenShawn/DeepEyes-Datasets-47k` dataset is one candidate for the
general active-perception/reasoning portion of policy RL training. Dataset
selection and the pilot manifest remain `[TBD]`; the framework skeleton must not
hardwire this source.

Ingestion rules:

1. download and version the raw dataset;
2. retain raw image, question, ground truth, data-source metadata, and any useful identifiers;
3. discard or ignore the old rendered DeepEyes tool prompt;
4. render our own selected-family native TGVF tool prompt at runtime;
5. do not assume DeepEyes crop-specific formatting is valid for TGVF;
6. hash images and normalize questions for leakage checks;
7. preserve source metadata for reward routing and analysis.

Suggested canonical sample schema:

```json
{
  "sample_id": "...",
  "images": ["..."],
  "question": "...",
  "ground_truth": "...",
  "answer_type": "choice|short_text|number|math|open_text",
  "data_source": "...",
  "metadata": {}
}
```

Do not store a single irreversible rendered prompt as the canonical source.

## 9.4 Required data audit, not ablation

Before training, run base Qwen3-VL-8B-Thinking multiple times per candidate
sample and record:

- pass rate;
- output length;
- answer-verifier confidence/type;
- whether the sample appears malformed;
- whether the answer is reliably verifiable.

This is used to understand the dataset and construct a pilot pool. It is not a large experiment matrix.

Also perform:

- exact and near-duplicate image checks against evaluation data;
- normalized question overlap checks;
- broken-image checks;
- missing/ambiguous answer checks;
- source-distribution summary.

The pilot dataset size is provisional. A range such as 2K–5K may be used after throughput calibration, but do not hardcode this as a scientific conclusion.

## 9.5 Later TGVF-specific data

Plan a second data stream that better reflects TGVF’s distinctive strengths:

- texture recognition;
- fine-grained appearance;
- clutter and distractors;
- camouflage-like patterns;
- structured texture interference;
- target-conditioned evidence recovery.

This is not required to block the first RL infrastructure pilot.

# 10. Reward interface and candidate minimal design

Do not implement an elaborate shaped reward at project start.

## 10.1 Answer reward

The exact reward composition is `[TBD]`. Final-answer correctness is the
candidate primary signal, implemented behind a verifier router rather than
hardwired into the trajectory/runtime layer.

Implement a verifier router:

```text
multiple choice / fixed label
→ deterministic normalization and match

number / math
→ parser and rule verifier

short open text
→ normalized rule verifier when reliable

semantically variable open answer
→ optional LLM-as-a-judge
```

A large judge is not required for every dataset. DeepEyes used a large LLM mainly to judge semantic equivalence for open-form answers. That judge is not the same thing as an SDPO teacher.

Every reward record must log:

- verifier type;
- normalized prediction;
- normalized ground truth;
- raw verifier output;
- answer reward.

## 10.2 Format handling

Initially treat malformed behavior as a validity issue or penalty, not as a large positive reward for printing tags.

Check only what the environment needs:

- valid native tool-call parse;
- valid tool name;
- valid JSON arguments;
- nonempty target;
- valid final output.

## 10.3 Conditional tool bonus

Keep an optional trajectory-level conditional tool bonus in the configuration, inspired by DeepEyes:

```text
tool used
+
final answer correct
→ optional bonus
```

Do not reward every tool call separately by default, because repeated calls must not become reward farming.

The decision to enable this bonus and its coefficient remains open.

## 10.4 Rewards explicitly excluded from the first implementation

Do not add these as initial optimization signals:

- target semantic-quality reward;
- observation-quality reward;
- reasoning-preservation reward;
- per-call reward;
- complicated hand-built target scoring.

Track related diagnostics separately.

## 10.5 Target leakage diagnostic

Log whether a target appears to copy an answer option or answer-only value.

This is initially a diagnostic, not a reward term. Avoid naïve substring rules that flag legitimate entity descriptions. Keep raw evidence in the trace for manual inspection.

# 11. SDPO design boundary

SDPO support must be built into the architecture, but optimizer execution stays
fail-closed until its mathematics, state lifecycle, and multimodal parity tests
pass. Interface work may proceed in parallel with GRPO; it is not a retrofit
after the GRPO pipeline is complete.

## 11.1 Initial objective modes

```text
grpo
sdpo
hybrid_tbd
```

`sdpo` means reference-style SDPO whose distillation loss replaces the policy
loss. `hybrid_tbd` is only an extension slot; it must not become executable or
be named `grpo_sdpo` until an exact combined equation is accepted. The first
multimodal pilot may use GRPO while SDPO parity proceeds in parallel. This is an
execution order, not a decision to exclude SDPO.

## 11.2 Teacher behavior

SDPO's teacher is self-distillation, not an external answer judge.

Keep teacher mode configurable:

```text
stop-gradient current-policy self-teacher
EMA teacher regularization
trust-region teacher regularization
```

Freeze initialization, update timing/rate, interaction with the separate KL
reference, LoRA/full parameter mapping, FSDP2 sharding/offload, and resume
before choosing a mode.

## 11.3 Feedback, teacher context, and alignment

The trajectory schema must separate:

- scalar reward and the success threshold/decision;
- typed environment textual feedback;
- optional answer-judge feedback with full provider identity;
- group identity and selected successful demonstration provenance.

The teacher-context builder consumes the complete native multi-call trajectory,
not only the final user message and one terminal response. It returns an exact
template/version/hash, truncation report, and alignment from every original
policy-sampled assistant token to its teacher-context position. Truncation that
breaks an aligned response fails closed.

Teacher replay may change the accepted feedback-conditioned **text context**,
but it must consume immutable handles to the rollout-recorded original image
and every call's main `D`, D-DeepStack, layout, M-RoPE positions, masks, and
cache contract. It never regenerates or replaces the observation with text.

## 11.4 Distillation targets and multimodal masks

Teacher/student losses must not be applied to environment-provided image observations as if they were generated policy tokens.

Required masks must distinguish at least:

- original prompt tokens;
- assistant reasoning tokens;
- tool-call tokens;
- environment/tool-response text;
- image observation tokens;
- post-tool assistant tokens;
- final-answer tokens.

All masks and token counts must be logged for debug runs.

The distillation-target record must identify full-logit or top-k-plus-tail mode,
student-selected token IDs when applicable, teacher/student log probabilities,
valid-token and sample masks, teacher policy/state version, context hash, dtype,
and numerical/storage convention. Full-logit memory and approximation error are
measured rather than hidden behind a framework default.

## 11.5 Checkpoint and parity gate

Before using SDPO on TGVF:

1. reproduce a tiny official/reference text SDPO run;
2. compare teacher-context construction, loss values, importance weighting, and
   one-step parameter updates on a fixed seed;
3. verify teacher/EMA/trust-region weights, update counter, config, RNG, group
   state, template identity, checkpoint, and strict resume;
4. verify top-k-plus-tail approximation against full logits if used;
5. add unit tests for multi-turn alignment, truncation, padding, masks, and
   exact recorded-observation replay;
6. run a two-call Qwen3-VL-8B-Thinking multimodal forward/loss test under
   FSDP2;
7. run the declared `Qwen/Qwen2.5-VL-7B-Instruct` family-adapter fixture before
   claiming cross-family SDPO compatibility.

# 13. Pilot training policy

The first pilot must be small enough to iterate.

Hardware target:

```text
4 × B200
```

Desired end-to-end wall-clock envelope:

```text
approximately 10–24 hours
```

Do not launch a one-week pilot merely to discover a broken tool loop or zero reward variance.

## 13.1 Pilot defaults

- Qwen3-VL-8B-Thinking;
- DeepStack enabled;
- newly trained native-format TGVF Adapter checkpoint;
- LoRA for the base policy by default;
- TGVF Adapter frozen for the first policy RL proof;
- multi-call AgentLoop enabled;
- veRL/GRPO adapter skeleton available, with execution blocked until the exact
  GRPO contract is accepted;
- SDPO extension boundary present from the first skeleton; execution remains
  disabled until its equations, teacher/state contracts, and parity gate are
  accepted;
- reward interface present, with unresolved reward choices left `[TBD]`;
- full trajectory tracing for a diagnostic subset.

Do not freeze exact group size, total steps, or dataset size in this specification. First run a throughput calibration and propose a configuration that fits the time envelope.

## 13.2 Throughput calibration report

Before the pilot, Codex must produce a short report containing:

- rollout engine and exact versions;
- average prompt tokens;
- average generated tokens;
- average number of tool calls;
- time per rollout;
- image/TGVF latency;
- actor update latency;
- GPU utilization and peak memory;
- estimated total runtime for candidate configurations.

## 13.3 Pilot success indicators

The pilot is considered informative when:

- valid tool calls appear and do not collapse to zero;
- multiple-call trajectories are possible;
- target strings are parseable;
- D is returned and reasoning continues;
- reward has nontrivial variance;
- tool use is sometimes associated with better answers;
- no-tool behavior does not catastrophically regress;
- reasoning length does not collapse across the board;
- checkpoints resume correctly;
- throughput is compatible with further iteration.

## 13.4 Early-stop conditions

Stop and debug when:

- tool calls are nearly always malformed;
- tool calls remain exactly zero;
- all group rewards are identical;
- image response breaks continuation;
- repeated calls loop indefinitely;
- TGVF observations are not actually consumed;
- reward verifier is clearly wrong;
- no-tool accuracy collapses quickly;
- target leakage becomes dominant;
- runtime estimate exceeds the pilot envelope without a clear bottleneck plan.

# Appendix A — Texture/interference robustness memo

## A.1 Hypothesis

TGVF’s distinctive advantage may be target-conditioned recovery under visual interference, not only spatial zoom on tiny objects.

A useful evaluation should test whether TGVF can recover relevant evidence when the image contains irrelevant or disruptive texture patterns.

## A.2 Paired benchmark design

For each clean benchmark image, create paired perturbed versions using controlled transformations such as:

- semi-transparent fabric-like textures;
- repeated stripes or checker patterns;
- structured high-frequency patterns;
- clutter overlays;
- camouflage-like patterns;
- local distractor textures;
- multiple severity levels.

Constraints:

- ground truth must remain unchanged;
- the transformation must not fully occlude the answer evidence;
- clean and perturbed samples must remain paired;
- perturbation parameters and random seeds must be recorded;
- human spot checks are required.

## A.3 Later comparison

```text
Qwen3-VL baseline
Crop
TGVF
Crop + TGVF
```

Metrics:

- clean accuracy;
- perturbed accuracy;
- absolute accuracy drop;
- recovery over the perturbed baseline;
- performance by texture type and severity.

Possible recovery metric:

```text
(TGVF perturbed accuracy - Base perturbed accuracy)
----------------------------------------------------
(Base clean accuracy - Base perturbed accuracy)
```

This memo is a future dataset/evaluation direction. It must not delay the initial RL infrastructure and pilot.
